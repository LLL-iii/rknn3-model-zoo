# LLM Model Modification Guide

For LLM models, the coprocessor is primarily used to accelerate the main neural network part of the LLM and the sampling post-processing. Operations like the Tokenizer, post-processing, and the coupling between multimodal models currently require assistance from the host's CPU/NPU.

The coprocessor currently has **no special restrictions** on the model's inputs and outputs. However, to achieve **optimal inference performance** on the hardware, RKNN has established a set of LLM inference interfaces and a workflow based on the coprocessor's hardware characteristics. This workflow requires that **LLM models** meet certain requirements when being exported to ONNX. The specific requirements are as follows:



## Description of Files Generated by Deployment Examples

This repository provides model conversion and on-board deployment examples, primarily based on classic models from HuggingFace. The conversion scripts mainly consist of three parts: `export_llm.py`, `export_vision.py`, and `export_rknn.py`. Their functions and the files they generate are as follows:

1) `export_llm.py` exports ONNX models and related configuration files from LLM files in HuggingFace format. The generated files are:

- **model_llm.onnx**: An ONNX model file adapted for RKNN3-Toolkit. By default, it uses an external GRQ quantization algorithm, and the model itself contains quantization parameters. If the external GRQ quantization algorithm is not used, quantization can be performed during the model conversion process using the RKNN3-Toolkit.
- **model_llm.config.pkl**: A configuration file required by RKNN3-Toolkit to convert LLM models. It includes parameters describing the model's specifications, such as chat template, vocab size, hidden size, as well as information related to the external GRQ quantization algorithm.
- **model_llm.embed.bin**: The weights of the model's Embedding layer, stored in Float16 format. Currently, the Embedding layer operations are handled on the host side. The host queries the corresponding Embeds data based on Token IDs and transmits it to the coprocessor. If the model's Embedding layer operations are complex, the `model_llm.embed.bin` file may not be present. In this case, the user needs to manage the Embedding operations within their application logic.
- **model_llm.tokenizer.gguf**: The model's Tokenizer file. The RKNN3 on-board deployment supports Tokenizer functionality by default and requires the corresponding Tokenizer file for initialization. This file can be ignored if a custom Tokenizer is used.

2. `export_vision.py` supports exporting Vision ONNX models from HuggingFace, which includes:

- **model_vision.onnx**: An ONNX model file adapted for RKNN3-Toolkit. It does not support external quantization.

3. `export_rknn.py` supports converting ONNX models to RKNN format, which includes:

- **model.rknn**: The RKNN model file.
- **model.weight**: The weight file for the RKNN model.



## Input/Output Restrictions and Meanings for LLM Models in ONNX Format:

**Model Input:** Must include and only include the following 4 inputs:

- **input_ids**: The input token IDs, with a dimension of `[1, sequence]` and data type `int64`.
- **attention_mask**: The causal inference mask for the input, with a dimension of `[1, sequence]` and data type `float32`. It is mainly used to control the impact of padding empty inputs on inference under a fixed input shape.
- **position_ids**: Configures the position encoding IDs for the input, controlling the sampling points of RoPE.
- **logit_id_to_keep**: Retains the logits output result for the corresponding ID. This is mainly used in the prefill stage to keep the last valid logits output, reducing redundant computation and memory overhead.

**Model Output**:

- The output is a single logit output.



## KV Cache:

- When loading an LLM model, RKNN3-Toolkit automatically constructs the internal management logic for the KV cache based on the Attention op, including optimizations for inference performance and cache quantization. **Users do not need to manage the KV cache themselves**. For this feature to be enabled, the ONNX model must not have KV cache inputs or outputs. This can usually be achieved by setting `use_cache` to `False` in the LLM model's config when exporting the model, which will result in an ONNX model without KV cache inputs or outputs.



## Support for Multiple Input Shapes:

- RKNN does not currently support real-time dynamic shapes but supports multiple static shapes. Users need to specify the shapes required for their model application in advance. For example, in an LLM support scenario, the prefill stage requires an input of length N for faster inference performance, while the generate stage uses an input of length 1 for causal inference.
- By configuring the `seq_len` parameter in the `rknn.load_llm` interface, for example, by setting `seq_len = [1, 64]`, a prefill model with an input token length of 64 and a decoder model with an input token length of 1 will be generated.
